## TECHNICAL PRINCIPLES
- `{"field": null}` ≠ `{}` (field absent) — completely different semantic meaning
- Nullable: `"type": ["string", "null"]` — field present with null value
- Optional (not in required): field may be absent entirely — UNPREDICTABLE model behavior
- Pattern: make ALL optional contextual fields BOTH nullable AND in required array → forces explicit null signal
- `additionalProperties: false` + nullable fields interaction: model cannot add unlisted fields
- `default` values: not enforced by Claude — model may or may not use them; cannot replace required+nullable pattern
- `oneOf: [{"type":"string"},{"type":"null"}]` vs `"type":["string","null"]` — both valid, same semantic
- Multiple nullable fields: 3+ nullable fields in same schema — all must follow same pattern
- Validation cascade: model outputs `{}` missing nullable field → downstream treats as "no data" → wrong business logic
- Retry with schema error: on validation failure, include exact field name and expected type in retry prompt
- Null vs empty string: `null` = "not applicable/unknown"; `""` = "applicable but blank" — semantically different
- Null vs 0 (for numbers): `null` = "not applicable"; `0` = "zero value, applicable" — same distinction
- Nested nullable: `address.apartment_number` nullable inside required address object — depth adds complexity
- Array nullable: `tags: null` vs `tags: []` — null = no tags field applicable; [] = applicable but empty
- Schema documentation: `"description"` field in schema helps model understand WHEN to output null vs value
