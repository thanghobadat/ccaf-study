## TECHNICAL PRINCIPLES
- Dynamic few-shot: select examples at runtime by semantic similarity to current input (RAG-style)
  - Benefit: most relevant examples for each specific input
  - Cost: retrieval latency + embedding model dependency
- Static few-shot: fixed examples baked into system prompt
  - Benefit: simple, predictable, zero latency overhead
  - Risk: stale if distribution shifts
- Dynamic few-shot failure: wrong similarity metric → dissimilar examples retrieved → worse than static
- For structured JSON output: show complete example of EACH distinct schema shape the model might produce
- For code generation: examples must show correct syntax for the target language/framework
- For extraction tasks (slot filling / NER): examples must cover all entity types to extract
- Few-shot chain-of-thought: include reasoning steps in examples → model learns to reason, not just classify
- System prompt + examples relationship: system prompt states the RULE; examples show APPLICATION of rule
- Context window budget for examples: at 3-8 examples for simple tasks; scale up only for complex multi-step
- Separator clarity: examples must use clear delimiters so model knows where input ends and output begins
- Cross-domain contamination: examples from domain A used for domain B task → wrong patterns transferred
- Retrieval-augmented few-shot: vector DB stores labeled examples → top-k retrieved per request
- Example freshness: examples should be updated when production distribution shifts (monitored, not static forever)
- Zero-shot vs few-shot threshold: for tasks Claude already handles well, few-shot adds no value
