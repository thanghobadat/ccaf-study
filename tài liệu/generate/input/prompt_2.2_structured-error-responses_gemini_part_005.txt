## TECHNICAL PRINCIPLES
- NEVER return same signal (empty array, null, generic string) for semantically different error types
- Error categories and their required fields:
  - Permission/Auth error: {"error": "ACCESS_DENIED", "retryable": false, "message": "..."}
  - Not found (valid empty): {"results": [], "count": 0, "message": "No matching records"}
  - Transient/retryable: {"error": "SERVICE_UNAVAILABLE", "retryable": true, "retry_after_seconds": 30}
  - Validation error: {"error": "INVALID_INPUT", "field": "date_of_birth", "message": "Expected YYYY-MM-DD"}
- retryable boolean: model uses this to decide whether to retry or escalate to human
- error_code vs message: error_code is machine-readable for branching; message is human-readable
- Structured errors enable model to: retry transient errors, escalate auth errors, correct input validation errors
- Unstructured errors ("Error: something went wrong") → model cannot take appropriate action
- Tool MUST distinguish: (a) empty result, (b) error (permission), (c) error (not found), (d) error (input invalid)
- Downstream agent impact: if tool conflates errors, downstream logic makes wrong decisions
