## TECHNICAL PRINCIPLES
- Tool description: clearly state WHAT the tool does, WHEN to use it, WHAT it returns, and WHAT errors it may throw
- Granular tools: one tool per action (read_customer, update_customer, delete_customer) > monolithic manage_customer(action)
- Benefit of granular: clearer model reasoning, safer (can give read tool to read-only subagent), easier audit
- Parameter descriptions: guide model to use correct types  Einclude format examples in description
- enum constraints: use enum for fixed value sets  Eprevents model from guessing
- pattern constraints: use regex pattern for structured strings (phone numbers, IDs, dates)
- required vs optional parameters: make the model explicit about what's needed
- Tool return schema: document the return value shape so model knows what to expect
- Ambiguous tool names: model may call wrong tool; fix with clear naming + descriptions
- Over-broad tools: a tool that does everything is hard to reason about and unsafe
- Tool for read vs write: separate read tools from write tools for safety
- Error documentation in tool schema: list possible error codes and their meanings
- Input validation in tool implementation: validate before executing  Ereturn structured error, not exception
- Tool naming conventions: use verb_noun format (get_customer, create_order, delete_file)
