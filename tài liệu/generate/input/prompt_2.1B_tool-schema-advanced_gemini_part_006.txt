## TECHNICAL PRINCIPLES
- Return schema documentation: model must know what the tool returns to interpret it correctly
- Undocumented return fields: model may hallucinate field names that don't exist
- Error codes in return schema: list possible error objects — model decides to retry, use fallback, or escalate
- Tool granularity decision: too granular (30 tiny tools) is as bad as too monolithic — aim for coherent actions
- Required vs optional parameters: optional params model may skip; required must be explicit
- Nested parameter objects: complex schemas can confuse model — flatten where possible
- Array parameters: model may pass single item instead of array when not clearly typed
- Input validation in tool implementation: validate before executing — return error, not exception
- Idempotency documentation: tool is/isn't safe to call twice — model needs this for retry decisions
- Conflicting tool results: two tools return different data for same entity — model must pick authoritative source
- Tool chaining design: tool A output feeds tool B input — schema must be compatible
- Tool versioning: v1 and v2 of same tool exist — model picks wrong version without clear description
- Side effects documentation: tool has side effects (sends email, charges card) — model must know to call once only
- Rate limit documentation: tool is rate-limited — model should batch or add delay between calls
